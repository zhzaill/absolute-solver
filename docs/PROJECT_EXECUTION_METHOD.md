# 任务回收后的项目推进方式

版本：v1.0
日期：2026-10-26
适用范围：Absolute Solver 的需求回收、实现、验收和归档

## 1. 总原则

需求明确优先。技术方案只有在满足明确需求、权威边界和验收条件后才能进入实现。

一次只推进一个可验收的主任务。其他发现的问题先记录为任务，不在当前任务中无边界扩张。

## 2. 任务回收流程

### 阶段 A：冻结和盘点

1. 暂停新增功能和架构迁移；
2. 读取 `docs/REQUIREMENTS_INDEX.md`、领域手册、项目基线和最近运行报告；
3. 检查 `git status`、最近提交、未提交修改和正在运行的服务；
4. 收集代码、报告、日志、用户明确要求和未完成清单；
5. 历史计划只作为候选来源，不直接视为当前任务。

### 阶段 B：去重和定性

每个候选事项必须归入以下一种：

| 类型 | 处理方式 |
|---|---|
| 明确需求 | 生成任务卡，进入排序 |
| 已完成但缺证据 | 只补验收和报告，不重写实现 |
| 文档与实现不一致 | 生成纠偏任务，先确定权威来源 |
| 历史计划 | 标记为归档或重新确认，不自动执行 |
| 新想法 | 放入候选区，不能抢占当前主任务 |

### 阶段 C：排序

优先级固定为：

1. P0：权限、安全、数据损坏、错误路由、协议权威冲突；
2. P1：核心用户链路无法完成，例如 Native TTS、ASR、Body 接管；
3. P2：可观测性、部署、恢复、发布和维护质量；
4. P3：性能优化、替代技术、gRPC、流式 TTS 和非必要体验增强。

同一优先级内，先处理阻塞其他任务的依赖，再处理用户可直接验证的链路。

## 3. 任务卡要求

任务卡放在 `D:\11\Projects\Absolute Solver\docs\tasks\YYYY-MM-DD-<task-id>.md`，至少包含：

```text
任务 ID：
需求来源：用户 / 要求手册 / 缺陷 / 验收报告
目标：一句话说明要改变的行为
优先级：P0 / P1 / P2 / P3
范围：允许修改的模块和文件
不在范围：明确排除的相关事项
前置条件：服务、配置、设备、权限
输出位置：代码、测试、报告和临时产物的绝对路径
验收条件：可执行、可观察、可判定
风险与回滚：失败时如何恢复
状态：captured / ready / active / blocked / verify / accepted / archived
```

没有输出位置和验收条件的事项不能进入 `ready`。

## 4. 实施循环

每个主任务按以下顺序推进：

1. `captured`：记录原始需求和来源；
2. `ready`：补齐范围、依赖、输出位置和验收；
3. `active`：先读取现状，再做最小实现；
4. `verify`：运行与风险匹配的测试和真实 smoke；
5. `accepted`：代码、测试、运行报告三类证据齐全；
6. `archived`：把结果写回领域手册和项目基线。

遇到阻塞时进入 `blocked`，必须记录阻塞原因、需要的外部条件和下一步，不得用“暂时完成”掩盖。

## 5. 每个任务的验收证据

至少选择与风险相匹配的证据：

- 协议或数据结构：单元测试、schema 检查、往返测试；
- Hub/Body 路由：双 Body、断线、handoff 和错误 smoke；
- Provider：真实 HTTP 状态、响应格式、延迟和降级；
- TTS：`D:\11\Logs\tts\` 下诊断 WAV 加上实际 Native 播放结果；
- Presence：授权、TTL、撤销和 Host 生命周期报告；
- 机器人：只读投影、帧年龄、运动租约和 watchdog 证据；
- 发布：干净工作树、版本号、tag、构建和回滚记录。

模拟服务可以验证协议逻辑，但不能单独证明生产链路完成。

## 6. 任务回收后的当前推进顺序

按当前项目状态，主线顺序是：

1. 对齐协议文档、实现和 schema，处理未知 `type` 兼容性声明（已验收，见 `D:\11\Logs\2026-10-26-protocol-unknown-type.md`）；
2. 完成 Native Audio Body 的真实 TTS 播放闭环（已验收，见 `D:\11\Logs\2026-10-26-Absolute-Solver-TTS正式验收.md`）；
3. ASR 实麦通路（已按操作者判定于 2026-10-26 收口为 accepted，见 `D:\11\Logs\2026-10-26-ASR实麦诊断与录音台.md`）：根因是输入设备电平而非系统缺陷；人工朗读逐字一致的补证排在 2026-10-27，另需修复内置阵列送全 0；
4. 收尾 Presence 覆盖层生命周期和撤销审计；
5. 完成机器人导航/运动安全的剩余验收；
6. 清理未提交改动、生成运行报告并准备 release；
7. 只有 gRPC 触发条件成立后，才创建 proto 和迁移任务。

## 7. 汇报格式

每次任务回收或阶段收束都输出一份报告到 `D:\11\Logs\`，包含：

- 本次回收了哪些需求；
- 哪些已完成、部分完成、未开始或阻塞；
- 每项的代码、测试和报告位置；
- 新发现的文档与实现不一致；
- 下一项唯一主任务及其验收标准；
- 不做的事项和原因。

报告不能只写“完成”。必须写完成的行为、验证方式、产物路径和剩余边界。

## 8. 禁止事项

- 未明确需求就开始 gRPC、流式 TTS 或大型框架迁移；
- 把浏览器演示、模拟 Provider 或历史报告当作生产验收；
- 在未完成当前主任务时并行展开多个高风险主线；
- 通过改文档勾选项代替代码和运行证据；
- 把临时输出写入仓库、长期记忆、trace 或未声明的目录；
- 遇到阻塞时继续扩大范围而不记录阻塞。
