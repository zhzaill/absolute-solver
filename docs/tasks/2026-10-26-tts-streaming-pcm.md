# Provider 侧流式 PCM

任务 ID：tts-streaming-pcm
需求来源（建卡时）：用户 2026-10-26 指令「另立任务实现 Provider 侧流式 PCM，例如 GPT-SoVITS 分块或 `openai_sse`」；`docs/TTS_REQUIREMENTS.md` §9.1「Provider 流式 PCM 的最低要求」。
目标：把"Provider 一次返回整段 WAV"改为"Provider 边合成边吐 PCM 块"，让首块音频的等待时间由**首块合成时间**决定，而不是整段合成时间。
优先级：P3（体验优化；不得抢占 P0/P1）。
状态：**planned**（未开始；未写代码、未改协议、未接任何 Provider 的流式接口）

## 1. 与已完成能力的分界（本卡存在的理由）

分段 TTS 已完成（`docs/tasks/2026-10-26-tts-segmented.md`，accepted）。它把"长文本的一次长等待"拆成"多个短等待"，但**每个段仍然是一次完整的 WAV 请求-响应**。以下四样东西都**不是**流式 PCM，不得作为本卡的完成证据：

| 东西 | 为什么不是流式 |
|---|---|
| `seq` 段序号 | 只是分段序号，段内仍是完整 WAV |
| 分段 WAV（`-t<turn>-s<seq>.wav`） | 每段仍等整段合成完才落盘/发送 |
| `say.audio` 的 `pcm16-binary` 二进制帧 | 只是传输编码优化，不改变合成模型 |
| `audio.up` 输入分片、`mouth` 口型采样 | 前者是上行麦克风分片，后者是口型采样，都不是 TTS 下行流 |

判定标准只有一条：**首块可播放音频到达 Hub 的时刻，必须早于该段整体合成结束的时刻**，并且这个"早"必须能用 Provider 侧的流式语义解释，而不是 Hub 自己切片。

## 3. 最低设计要求（对应手册 §9.1 的七条）

1. **文本与块的边界**：明确一段文本对应一条流；块只是段内的 PCM 分片，`seq` 语义不变。不得让"块序号"和"段序号"共用一个字段。
2. **首块契约**：Provider 必须给出可判定的"块就绪"信号（分块响应体、SSE 的 `data:` 事件或等价物）。Hub 收到第一块即解码并发送，不等待后续块。
3. **取消语义**：打断必须能真正中止 Provider 侧的合成（关闭流/断开连接），并记录"已中止"；不得只在 Hub 侧丢弃已收到的块而让 Provider 继续烧 GPU。
4. **失败与降级**：首块前失败 → 与本卡外既有语义一致（整回合字幕降级）；首块后失败 → 已播部分不重播，剩余段落文字幕。不做无界重试。
5. **解码**：流式块可能是裸 PCM（附采样率/位宽/声道）或流式 WAV 头 + 裸 PCM。两种都必须显式声明，不得靠嗅探猜。位宽/声道不匹配时记明确错误，不得静默播放杂音。
6. **可观测性**：每段记录"首块延迟"与"整段合成完成延迟"两个数，并记录块数、块间隔（有界）、是否被取消。验收报告必须同时报告这两个数，只报 HTTP 200 不算完成。
7. **输出位置**：正式 PCM 仍只允许 Hub 内存 → active Body；诊断 WAV 只在显式 `SOLVER_OUTPUT_WAV`（且已由 `D:\11\Logs\tts\` 守卫校验）时落盘；报告写入 `D:\11\Logs\YYYY-MM-DD-tts-streaming-pcm.md`。

## 4. 判定"真流式"的验收条件

1. **首块早于整段**：同一文本，`首块延迟` 必须显著小于 `整段合成延迟`（建议阈值：首块 ≤ 整段的 50%，且首块 ≤ 该段 PCM 时长的一半），并在报告中给出两者原始数字。
2. **块到达节奏**：块间隔必须与合成进度相关（单调推进、无"生成完再一次性吐完"的悬崖）。若所有块在整段合成结束后 < 100 ms 内集中到达，判定为"假流式"，本卡不通过。
3. **取消有效**：打断后 Provider 侧的合成任务必须终止（用 Provider 侧日志或 GPU 占用下降作为证据，不能只看 Hub 日志）。
4. **不回归**：`SOLVER_TTS_SEGMENTED=1` 的分段路径与 `=0` 的批量路径在流式关闭时逐项不变（`cargo test` 全绿 + 至少一次实跑复核）。
5. **不叠加**：本卡 v1 只允许"分段 + 段内流式"或"流式关闭"两种组合；**不允许**同时开两套切片逻辑（既切文本又切块却分不清是谁产生的空档）。
6. **不冒充**：报告必须显式声明该次验收用的是哪种判定证据；不得把分段 WAV、`seq` 递增或二进制帧当作流式证据。

## 5. 风险

| 风险 | 缓解 | 残留 |
|---|---|---|
| Provider 的"流式"其实是整段合成后分块发送 | §4.2 的块节奏判据 + Provider 侧证据 | 小模型短句下判据可能不灵敏，需要长文本用例 |
| 段内流式 + 段间并发导致 GPU 抢占，首块反而变慢 | v1 允许并发降到 1；实测对比后再定 | 长文本下可能退化为分段更优 |
| 取消不可靠（HTTP 连接断了但服务端继续算） | 记录取消结果，报告不得声称"已省下算力"除非有服务端证据 | Provider 实现差异 |
| 裸 PCM 采样率/声道不一致 | 显式声明 + 解码校验 + 失败即降级 | — |

## 6. 回滚

流式由独立开关门控（例如 `SOLVER_TTS_STREAMING`，默认关闭）；关闭即回到已验收的分段 WAV 路径。任何流式实现都不得改变 `SOLVER_TTS_SEGMENTED` 与批量路径的既有语义。
